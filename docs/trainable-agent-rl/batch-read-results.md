日期：2026-11-07，分支 `experiment`。按[冻结协议](batch-read-plan.md)完成32/32条同期
开发对照，源码hash全程一致，没有训练，也没有打开新test。当前目标仍未完成。

8题×2seed×2组；两组均原Prompt、interactive、相同初始4B零LoRA策略与预算。
控制组提供原四工具，处理组额外提供read_files；工具Schema及其上下文开销属于干预。

成功率配对差0，控制组-only与处理组-only各1对，均在billing家族的不同重复中。
四个家族聚合差均为零，因此family bootstrap区间退化为[0,0]；这不是等效性证据。
只有8题、4家族、重复开发使用，没有训练seed重复，不支持广泛泛化或稳定收益结论。

处理组平均少0.6875次工具调用，约5.98%；总Token反而多2.34%，格式拒绝也更多。
两组成功数相同，Token/成功也增加2.34%。不能宣称效率改善或推断复杂推理更好。
延迟包含服务/网络与控制面，未据这些小样本点估计宣称稳定加速或减速。

## 为什么离线节约回合没有转化成稳定收益

脚本控制可把12步降到7步，但真实模型只在7/16条处理组轨迹中成功使用批量工具，
合计10次成功调用、请求28个文件、截断项0。只读路径与输出边界保持不变。

另有14次批量调用被拒：9次Schema无效全部是请求文件数超过4；5次路径拒绝。
例如模型一次要求读取6个源码文件；还有`solve.py`、`editable/service.py`等不存在路径。
处理组另外5次单文件路径拒绝。格式拒绝和参数错误分别统计，不把正常失败测试算作无效工具。

因此“有工具”与“可靠使用工具”仍有差距。新增能力还令初始Schema增加150 Token；
后续反复携带、错误调用与不同决策共同影响总量，不能把全部增量归因于某一个因素。
成功使用新工具者属于事后选择的子群，不以其成功率推断因果效果。

## 反馈修复证据及不足

首次出现修改后公开失败反馈的step，控制组三条为12、12、11，处理组三条为12、10、8。
这些是发生失败反馈后的条件样本，任务/重复不同，不据此宣称配对平均反馈时间改善。
控制组2条、处理组1条在所有此类反馈后都没有后续真实采样。

两条实际反馈修复轨迹均为`mini_billing_1`：

- `paired-01_029_batch_read`：先成功批量读取，第一次Patch后的公开测试失败，之后新Patch，
  最终独立通过；控制面复评第一次候选失败，满足H2轨迹代理。
- `paired-01_031_single_read`：同样有第一次Patch失败、公开失败反馈、后续Patch及独立通过，
  控制组也能走通该路径，不能把处理组这一条归因为批量读取独有收益。

处理组只覆盖billing一个家族；成功率差不为正，处理组-only成功仅1对。三个开发条件均
未达到，机制门槛保持失败，不改阈值、不补采样，不进入新RL Pilot或算法效果比较。
这比之前“没有任何公开失败反馈后成功修改”提供了更具体的可行路径，但远未证明稳定可学习。

其余四条多Patch成功轨迹没有首次Patch后的公开失败测试证据，不补认反馈恢复。
私有部分候选复评只在运行结束后完成，未泄漏给Agent，不改变原Reward或原始结果。

精确本地重放逐Token核对379次真实请求；另3次在SDK前因36k累计Token不足被拒绝。
处理组还有1条在Context Assembly阶段因重写请求超过6144输入额度失败；该条恰是
`029_batch_read`，最终已修改候选仍独立通过。任务成功与Loop/资源状态分开报告。
原错误码、usage_known=false及failed终态保留，派生核验不把原未知用量字段填零。

两组终态分别为15 budget_exhausted/1 finished，以及11 budget_exhausted/4 failed/1 finished。
32/32结果可判定，32条均有候选和独立verdict；没有用finished计成功或删除预算终止。
其中31条实际执行私有候选测试，另1条在候选策略/语法检查阶段拒绝，仍记失败；
结果覆盖率不等于私有测试执行覆盖率。
