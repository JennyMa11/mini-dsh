研究目标仍是先证明交互可学习性，再比较算法。固定80条队列、任务、seed、训练参数、
成功判据与测试分母均不缩减。本轮未新增真实模型、训练或服务会话，也未变更活动账本。

后续状态：[确认阶段资金门禁已离线实现并验收](staged-funding-results.md)。本文以下

## 1. 为什么不继续等待同一份旧账单“自动释放”预算

[上一轮整账期预审](closed-period-budget-coverage.md)确认选定工作空间账单19.01元，
但不能证明全部旧请求均被覆盖。本轮从冻结源码及原始轨迹进一步重建了Core分母：

| 旧队列 | 运行数 | 已完成模型调用 | 原始Trace调用起止（UTC，2026-11-06） |
| --- | ---: | ---: | --- |
| calibration-01 | 8 | 8 | 12:31:15–12:31:24 |
| calibration-02 | 8 | 64 | 12:33:29–12:34:37 |
| calibration-03 | 8 | 60 | 12:36:03–12:37:18 |
| smoke-train-01 | 8 | 59 | 13:00:52–13:02:39 |
| core-train-01 | 80 | 531 | 13:24:30–13:42:42 |
| core-eval-01 | 80 | 535 | 13:44:48–14:03:25 |

共192条已终结运行、1257次模型调用，逐调用核对原始Token、logprob数量、Trace用量、
运行Token合计和终态；无model_call_failed。这些只是执行/费用证据，不是192个成功任务。
加上SDK探针的1次采样，数量与Core账本1258个采样UUID一致。

但冻结`budget.py`将settled ID排序保存，`pytrio_backend.py`只生成本地随机UUID，旧
Token文件没有保存该operation ID。因此原始追加顺序和逐UUID关联不能从这些文件恢复；
数量一致不能单独证明对应关系。SDK探针的采样和logprob重算还缺少可靠的请求时间及
owned sampler标识，两项旧预留合计0.04元，不能因结果文件存在就归入某个账期。

旧31.38元分解为：按原计价规则重算的1258次采样25.16元，非采样**余额残差**6.22元。
73个具名操作按名称/源码意图分为compute 19、optimizer 19、save/snapshot/restore 35。
6.22不是逐操作账单重建；类别也不证明计费归属或发生时间。此前保留的10.06元包含
上述6.22及S0采样3.84，不能统称“管理费”或“重复预留”。

整池覆盖仍可能用单独的完整性、归属和时段论证成立，但本次没有足够证据作此结论。
继续刷新相同账单不会恢复已丢失的本地关联，不能把每次刷新当成释放额度的新证据。

## 2. 可行的替代路径及金额边界

目前活动保守占用42.667元，可用7.333元。当前控制器要求一次性容纳所有剩余动作，
固定完整分配20.302元，所以仍拒绝真实入口。该拒绝符合当前实现；本文件不绕过它。

可以另立资源策略：完整队列预先冻结，只在已确认边界为**下一个完整阶段**检查资金。
费用暂未结算且下一阶段资金不足时停止发起请求，保留队列并等待账单；不降低阈值、
改seed、重采样或删除未运行行。新增费用用新请求的完整证据结算，旧不明费用继续保留。

| 完整阶段 | 当前固定参数下的上界 | 计算 |
| --- | ---: | --- |
| Readiness全部16条及初始化 | ¥2.15 | 16 × 0.09 + 0.21 + 0.50 |
| 一个完整训练组，含4条rollout、backward、optimizer及两类保存 | ¥2.409 | 4 × 0.09 + 1.339 + 0.21 + 0.50 |
| 全部32条配对test | ¥3.38 | 32 × 0.09 + 0.50 |

表中0.50是同一笔剩余额外额度的保守上界，不是每阶段再收费0.50。初始LoRA校验
0.02和恢复均从该共享额度扣除。完整总分配仍为80 × 0.09 + 8 × (1.339 + 0.21)
+ 0.21 + 0.50 = 20.302元，没有把总预算改写成2.15元。

三个阶段各自均小于当前可用额，**不表示整个顺序现在可负担**。需要实际新账单低于
预留且覆盖复核通过，才可能释放后续资金；也可能仍无法完成。不得将尚未执行的行
当成通过，或把预算停止的部分实验描述成完整RL收益实验。这条路径不保证成功，
优势是可以在不释放旧不明费用、不提高50元上限的前提下先获得必要的Readiness证据。

## 3. 接入前必须完成的实现与验收

目前只完成源码评估，以下均是待开发能力。不得通过删除`_admit`检查或直接调用
SDK Runtime实现“分阶段”。原Agent Loop、工具权限和插件架构不需要改变。

| 模块 | 必需变更 | 验收证据 |
| --- | --- | --- |
| `learning_schedule.py` | 在新plan中固定资金策略；保留full_remaining旧模式；80行及20.302不变 | 新旧模式的case/seed/顺序/分母一致，模式无法事后切换 |
| `learning_execution.py` | 分别计算完整Readiness、下个未提交训练组、完整test所需费用；阶段边界才准入 | 没有足够组费用时，该组的首个rollout和任何SDK factory均未执行 |
| 同上 | 新增可恢复的awaiting_settlement；保持所有pending未知操作拒绝恢复 | 资金等待与取消、任务超限、readiness失败分开；未知optimizer绝不重放 |
| 同上 | 全局50元与原实验20.302元上界继续同时检查；共享额外额度只扣一次 | 费用上涨、Trace/报价未知、资金在途超量和输入变化均停止后续调用 |
| 恢复链路 | 目前最多2次恢复不足以覆盖10个阶段；重新声明有界恢复次数及成本 | 初始/当前policy、optimizer、sampler及文件hash一致；不重新初始化或重复更新 |
| `learning_prepare.py` / `learning_run.py` | inspect分别展示下一阶段和全队列需求，仍不能输出执行获准 | inspection无SDK副作用；CLI不能改变冻结的资源/科学参数 |
| 费用证据 | 新请求保存operation、资源/工作空间归属、时间、用量与回执关联；账单闭合再结算 | 不重用旧bill、不二次抵扣、不把预估差额当成实收退款 |

先为跨边界行为写契约与故障测试，再实现。至少覆盖：Readiness预算不足前置拒绝；
完整16条后才检查既有readiness门槛；训练组中途不能主动因可预见资金不足拆组；
确认回执后崩溃不双更新；没有新结算不能无界循环恢复；恢复额度耗尽停止；全部80行
跨阶段恢复后顺序不变；未运行项仍保留；旧full_remaining模式继续拒绝当前7.333元。
假SDK测试只能支持控制逻辑，不能写成新的学习或提供商实测结果。

实施前应以新ADR记录“整轮预留→固定阶段预留”的资源策略变化。旧prepared-01及其
源码/配置不改；新实现必须重新prepare并冻结新源码，再比较两份计划的科学字段。
资金模式、恢复上限和结算证据都要可审查，不能靠运行时临时改文件放行。

真实运行仍受用户“不要跑实验”的指令约束。本次只作评估，不由goal续行自动解释为
已批准付费采样或训练；后续若需启动，应先提供具体已验收入口、阶段上界和停止条件。
