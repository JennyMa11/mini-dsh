# ADR 0032：结构化笔记绑定正文，修订历史显式迁移

状态：Accepted（P3按冻结N01–N12功能验收通过，收益未测）。日期：2026-11-12（Asia/Shanghai）。

P2已通过[独立阶段验收](../results/memory-v2-p2-2026-11-11.md)。P3需要结构化规则、人工合并/替代和可审计历史；给旧记录补自由元数据会使新主张绕过旧批准，另写一个Markdown事实源又难以与SQLite状态原子更新。因此结构化笔记采用版本化JSON正文，历史与当前状态留在同一个私有SQLite事务中。

## 内容与授权

MemoryNote包含trigger、rule、verification、exceptions，以及sources与supersedes。verification只是“如何验证”的说明，不能承载accepted或批准结果。sources是带ID、修订、完整提议指纹、来源run与证据hash的来源关系；supersedes必须是sources子集，是待操作者批准的替代意图。关系本身不是新主张的验证证据。

整个规范JSON仍计入现有2KiB正文上限，字段、关系与例外全部进入原MemoryEntry内容hash/提议指纹。MemoryEntry schema 1和旧正文/批准bytes保持；不自动包装旧文本、不重签旧批准。未知笔记版本或额外字段拒绝；普通旧文本照常读取。关系最多五项，超出完整包裹预算时拒绝，不静默删来源。

合并/来源派生的笔记必须有新的专属来源run和新的证据hash；来源列表中的任一旧证据不能给新主张授权。受信服务还须重新核对同项目/版本的实际来源修订/指纹及来源证据。操作者确认的新环境证据或独立验证器的新结论仍经validate→approve→commit；新hash只保证完整性，不保证主张正确。结构化修订可显式绑定新的source_run_id，属于修订材料并清除旧批准；旧revise调用省略时保留原语义。模型仅能提议，不能提供权限、accepted或批准字段。

## 历史、替代与迁移

新增可选MemoryHistoryStore端口；旧MemoryStore实现仍可用于v1/P2读取。结构化维护要求显式支持历史的适配器；不支持时拒绝写入，不能悄悄退成丢历史的replace。

SQLite物理user_version 1→2仅由运行外的受权工具显式迁移；常规读取不升级。迁移保留entries现有payload原bytes，为每个当前记录建立migration_snapshot，明确更早历史未知。不得伪造过去各阶段的历史。物理迁移作用于被明确授予的整个数据库文件（包括其中其他项目），因此单列memory.migrate权限；回执只给版本/备份摘要，不暴露其他项目内容。单条维护/历史查询仍受显式project/version约束。旧程序遇到version2会拒绝；回退使用迁移前备份或受控导出，不丢弃新历史来伪装兼容。未知数据库版本、损坏/越界文件继续拒绝。

迁移先保存hash绑定的私有备份，再原子发布新数据库；在最后受控发布检查点前取消/失败保留旧数据库bytes，可能留下可审计备份，不能留下半迁移库。底层发布函数必须接收取消标记并在文件替换前统一检查；跨过该检查点进入原子发布后，取消或通知失败可能已提交，必须读回确认，不能宣称回滚。新空库可以显式初始化为version2，不必先写一条占位提议。已迁移库的重复迁移无状态变化。

version2每次创建/状态转换与历史追加同一事务、同一原子发布。历史记录保存完整旧/新状态、单调序号和操作类型，人工只读查询有分页与硬上限；原Trace保持不变。当前条目仍每项目100条，数据库仍8MiB；满时拒绝新写入，不淘汰历史或条目。

人工merge只产生新proposed结构化笔记。修订递增版本并撤销旧验证/批准；已批准替代的commit在单事务中校验全部旧引用、提交新条目、把被替代条目标为superseded并记录历史，失败时全部不变。新条目的supersedes关系必须已包含在被批准正文中，不能由commit工具临时附加。旧条目直到这一步仍有效，不在模型提议时自动撤销。关系节点按entry_id/revision/完整指纹区分；后续修订引用旧修订不被误判为ID环。来源只能解析到已committed的真实历史，互相引用尚未提交草稿不能成为授权链；自身替代、跨项目/版本和过期替代引用拒绝。运行内维护互斥、Tool Runtime/Permission、内容/来源保护、预算和无自动副作用重试继续适用。
