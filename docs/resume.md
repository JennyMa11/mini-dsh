## 一句话版本

**Mini-dsh｜Coding Agent Harness（个人项目，独立设计与实现）**
用 Python 从零构建可替换、可观测、可复现的 Coding Agent 运行时，通过单变量消融实验量化 Harness 设计对 Token 成本的影响：实测证明工具输出有界化可将单任务成本降低 **3.38 倍**；并把同一套 Harness 接到真实模型上跑通 18 次跨文件任务（成功率 100%、每次成功成本 **$0.000937**、Harness 自身仅占墙钟 **0.26%**）。

## 精简版（3 条，适合空间紧张的简历）

- **独立设计并实现**基于端口-适配器架构的 Coding Agent Harness（Python 3.12 / asyncio / Pydantic v2），落地完整 `Observe → Plan → Act → Execute` 循环、四层预算与四类终态，40 个源码模块、约 6,600 行实现。
- **构建可复现的单变量消融评测体系**：31 个任务覆盖 6 类编码场景、4 组消融套件（Context / 工具输出 / 权限反馈），实验读数逐字节可复现；实测定位工具输出是最大成本杠杆（**3.38×**），并量化检索类 Context 策略在长历史上反而增加 **40%** Token。接入真实 provider 后，同一套 Harness 在 6 个跨文件任务 × 3 次重复上跑出 **18/18 通过**、**86% 输入 Token 命中缓存**、**每次成功成本 $0.000937**。
- **落地默认拒绝的安全模型**（路径归属、符号链接防逃逸、deny-first 命令策略、host/protocol/port 网络白名单），以 **36 个攻击测试**覆盖 6 类攻击；工程门禁全绿：**201 个测试 / 覆盖率 86% / `mypy --strict` 零错误**。

## 完整版（可直接作为简历项目条目）

### Mini-dsh — 轻量级可评测 Coding Agent Harness

**个人项目｜独立承担架构设计、核心实现、评测体系与工程基建**

#### 项目目标

主流 Agent 项目把 Loop、Context、工具与权限耦合在一起，只能回答"能不能跑通"，无法回答"换一种设计会好多少"。本项目把 Harness 本身作为研究对象：在**模型不变**的前提下，量化 Context 策略、工具输出管理、权限反馈与执行隔离对**任务成本与成功率**的影响。

#### 技术栈

`Python 3.12` · `asyncio` · `Pydantic v2` · 端口-适配器架构 · `uv` + `hatchling` · `pytest`（unit/integration/e2e 三层） · `ruff` · `mypy --strict` · `Docker` · `GitHub Actions`

#### 个人职责

- 架构设计：端口-适配器分层（`domain / ports / runtime / adapters / application`）与显式组合根，无全局单例
- 核心实现：Agent Loop、Context 策略引擎、工具运行时、权限与沙箱、Benchmark 与消融框架
- 评测体系：任务集设计、指标定义、消融协议、结果归档
- 工程基建：质量门禁、CI、一键实验脚本、文档与 ADR

#### 主要贡献

**1. 端口驱动的 Agent Runtime（39 模块）**

- 实现完整 `Observe → Plan → Act → Execute → Observe → Continue | Finish` 循环，含步数 / Token / 工具调用 / 墙钟**四层独立预算**与四类显式终态
- 模型、Context、工具、Session、事件全部走 Protocol 端口，组合根单点装配；核心 Loop 不依赖任何厂商 SDK、Shell 或文件系统细节
- 插件运行时支持 `provides/requires` 依赖图校验、**依赖环检测**、启动失败**逆序回滚**与步骤边界热替换，覆盖率达 **100%**

**2. 可复现的单变量消融评测体系**

- 设计版本化 Benchmark manifest，逐任务钉扎 `repo_commit / seed / model / budget / isolation` 与成功判据，任务在隔离副本中执行
- 成功判定**完全依赖独立验证进程的退出码**，不采信模型自报完成
- 构建 **31 个任务**（`core` 25 个覆盖 6 类编码场景 + `repo` 6 个跨文件 Repo-Level 任务）与 **4 组消融套件**
- 设计 `stress` 套件（18 步长历史、75 KB 工具输出、含越权与逃逸动作），解决短任务无法区分 Context 策略的问题

**3. 默认拒绝的安全模型**

- 六道防线：工作区路径归属校验（含**符号链接防逃逸**）、deny-first 命令策略、网络 `host/protocol/port` 三元组白名单（默认 deny-all）、密钥文件拒绝、子进程环境变量 allowlist、超时后**进程组整体清理**
- 可选 Docker 硬隔离：只读根文件系统、`cap-drop ALL`、`no-new-privileges`、PID/内存/CPU 上限、默认断网
- 以 **36 个攻击测试**覆盖路径遍历、符号链接逃逸、Shell 注入、网络越权、密钥泄露、超时残留六类攻击

**4. 发现并修复导致实验结论失效的复现性缺陷**

- 现象：同一命令重复运行，Token 读数在 11,597 / 11,600 之间抖动，使所有消融对比失去意义
- 根因定位：Agent Loop 将墙钟 `duration_ms`（变长浮点）渲染进**模型可见的 Prompt**，导致输入长度随运行变化
- 修复：将计时数据限定在事件流（指标仍可读取），并补充回归测试锁定该不变量
- 结果：连续三次运行读数**逐字节一致**，复现性抖动归零

**5. 真实模型评测基础设施（`v0.2.0`）**

- 接入命名 Provider Profile（DeepSeek / OpenAI / Ollama）与带指数退避的瞬时错误重试；**价目故意不内置**：付费 provider 未声明费率时拒绝运行，避免静默报告 `$0` 污染成本结论
- 把「Harness 是否正确」与「模型是否够好」拆成两个可分别回答的问题：**9 个失败类别归并成 `success` / `harness` / `agent` / `environment` 四层**，每个诊断附带证据链
- 延迟拆成 `model / tool / harness` 三层，暴露脚本化模型下被模型延迟掩盖的 Harness 自身开销；成本区分 cached / uncached input 并给出 **cost per successful run**
- 实现 **Trace Replay**（不重新调用模型，逐步重建 `Context → Model → Tool Call → Observation → State`）与 **Trace Diff**（对齐两条 Trace，定位第一个行为分叉点及其 Token 代价）
- 报告加入 **Pareto trade-off** 分析：不只报"哪个最低"，而是给出被支配变体、支配者与差值，并在全并列时明确说明该轴无区分度

**6. 首次真实模型实测：把工程结果迁移到真实 provider（`v0.3.0`）**

- 在同一套 Harness 上跑通 `repo` 套件的 6 个跨文件任务 × 3 次交错重复：**18/18 通过**、`pass@k` 100%、成功率极差 0.00
- 实测经济性：**每次成功成本 $0.000937**、**86% 输入 Token 命中 prompt cache**；延迟拆解显示 **Harness 自身只占墙钟 0.26%**（16.4 ms / 6,410.1 ms），其余全是 provider 往返——这是"Harness 不是瓶颈"的量化证据
- **把报告变成自描述产物**：报告内嵌 profile / endpoint / thinking 开关 / `temperature_effective` / 显式费率，使成本数字脱离命令行历史也能被审计；并把真实模型数字纳入文档门禁（README 与归档报告不一致即测试失败）
- 完整性核查：18 条 Trace 中写入**全部落在源码文件**，对测试文件的写入为 **0**，排除"改测试骗过判据"

#### 量化成果

| 维度 | 结果 |
| --- | --- |
| **成本优化** | 工具输出有界化使单任务平均 Token 从 32,136 降至 9,511，**成本降低 3.38 倍**（$0.298 → $0.095），成功率不变 |
| **策略量化** | 定位检索类 Context 策略在长历史上反而增加 **40%** Token（12,617 vs 8,981）；基于 AST 的符号检索比整文件检索**省 27%** |
| **真实模型实测** | `repo` 套件 6 任务 × 3 次重复：**18/18 通过**、`pass@k` 100%；每次成功成本 **$0.000937**；缓存输入占比 **86%**；Harness 自身占墙钟 **0.26%**；对测试文件写入 **0** |
| **评测规模** | 31 个任务 / 4 组消融套件，单次全矩阵产出 **12 份实验报告**（10 份归档入库），一键脚本一键跑完 |
| **代码质量** | **201 个测试**通过、覆盖率 **86%**（核心 runtime **100%**）、`mypy --strict` 54 个文件零错误、`ruff` 零告警 |
| **可复现性** | 全部实验读数逐字节可复现；31 个任务 fixture 由生成器**逐字节可再生成**，每个 fixture 以 `sha256:` 摘要钉扎 |
| **交付完整度** | `v0.1.0` → `v0.2.0`（真实模型评测基础设施）→ `v0.3.0`（首次真实模型实测结果），wheel + sdist 已在干净环境验证安装 |

#### 可讲述的技术亮点

- **诚实标注边界**：明确区分"策略层"与"容器级隔离"，并在文档中写明"脚本化模型下成功率恒为 100%，只能得出成本结论、不能得出准确率结论"，避免用无效指标包装成果；真实模型上的 100% 同样标注了"6 任务 × 3 次、任务由 Harness 作者构造，不构成独立评测"
- **指标为 0 往往是 bug**：`permission_denied` 长期为 0，追查发现被拒绝的调用未发布事件，修复后 `stress` 套件才出现真实的拦截计数
- **文档与实验绑定**：归档脚本从实际运行结果派生汇总数据，杜绝文档数字与实验脱节；真实模型的成本数字与文档不一致会让测试直接失败
- **真实 provider 的坑只能用真实运行暴露**：DeepSeek 上游默认开启 thinking，而 thinking 模式下 API 会忽略 `temperature`，且带 `tools` 的请求必须原样回传历史 `reasoning_content`，否则直接返回 400。这个缺陷在脚本化模型下永远不会出现，是第一次真实运行才暴露的——也因此 harness 现在默认关闭 thinking，并把 `temperature_effective` 写进报告
